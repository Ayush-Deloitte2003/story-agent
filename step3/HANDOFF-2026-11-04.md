### Event intake and reliability

- `story.requested` CloudEvents enter through Dapr Pub/Sub and start the
  existing human-approved `story_workflow`. Event source and ID produce a
  stable workflow ID, so a redelivery maps to the same workflow.
- `POST /webhooks/story-requested` publishes through the app's Dapr sidecar.
  An HTTP acceptance means Dapr accepted the event, not that processing
  completed. Callers must reuse the event ID when retrying.
- Dapr Pub/Sub uses bounded exponential retries and routes exhausted deliveries
  to `story-events-dead`. There is not yet a DLQ consumer; those events remain
  for operator inspection.
- The publisher receives the Dapr workflow ID as its idempotency key. A repeat
  with identical content reuses the saved result; reusing the key with
  different content is rejected. This protects the publisher's filesystem
  side effects, but is not an end-to-end exactly-once guarantee.

### Independent story-quality reviewer

- Added the separate event type `story.quality-review.requested` on the existing
  `story-events` topic, with deterministic IDs distinct from writing workflows.
- The event carries a title and story, with an optional original request.
  `POST /webhooks/story-quality-review-requested` accepts the webhook;
  `GET /events/quality-review/{event_id}?source={source}` returns workflow state
  and the completed review.
- `story_quality_review_workflow` runs a separate reviewer activity with up to
  three total attempts. The result is validated as a score, `ready`/`revise`
  recommendation, summary, strengths, issues, and suggestions.
- `step3/scripts/verify_quality_review_recovery.py` persists the event identity
  across an app-pod replacement, replays that event, and verifies the recovered
  workflow ID and result.
- The reviewer prompt treats the story as content to evaluate, not instructions
  to follow. Its recommendation is advisory only. It cannot approve or publish
  a story and does not change the existing human-approval workflow.
- This event path is covered in the Kind run for successful completion and
  duplicate delivery, including restart/recovery and same-ID replay. The
  integration check also completes a review while a separate story workflow
  remains paused for human approval. This demonstrates independent lifecycle
  overlap in the single-replica demo, not load or multi-replica capacity.

## Suggested continuation

1. Before provider-backed capacity runs, confirm the provider quotas and a
   bounded test budget. Until then, do not enforce a concurrency cap or claim
   production scale.
2. Select DBOS or Temporal as the first comparison target. Use equivalent
   event inputs, agent calls, retry and persistence behavior, replica resources,
   and staged load; measure tail latency, queue delay/backlog, provider
   throttling, CPU/memory, and recovery.
3. Add observable retry/provider/backlog metrics before choosing deployment
   replica counts or autoscaling thresholds. A process-local semaphore would
   multiply with replicas and is not a deployment-wide limiter.
4. Design an Agent Inbox/DLQ handling path before consuming dead-lettered
   events. Do not silently acknowledge or discard failed events.

Continue to preserve the existing human approval boundary, REST behavior, and
the distinction between at-least-once event delivery and idempotent side
effects. Local Kind has not been validated on this machine.
